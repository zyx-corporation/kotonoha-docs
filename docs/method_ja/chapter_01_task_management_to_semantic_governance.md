# Chapter 1. タスク管理から意味統治へ

Status: draft / non-normative

本章は、Kotonoha Method の出発点を説明する。ここで扱うのは、既存のプロジェクト管理を否定する議論ではない。むしろ、Git、Issue、Pull Request、Project board、Milestone といった仕組みが有効であることを認めたうえで、それだけでは捉えきれない領域を明らかにする。

その領域とは、**意味の変化**である。

プロジェクトは、単なる作業項目の集合ではない。そこでは、目的が定義され、前提が置かれ、判断が行われ、成果物が作られ、責任が分配される。そしてそのすべては、時間の中で変化する。仕様は書き換えられ、実装は修正され、文書は要約され、AI生成物は人間の判断を補助し、ときには人間の判断そのものを曖昧にする。

Kotonoha Method は、この変化を単なる「進捗」や「差分」としてではなく、**意味・判断・成果物・責任の系譜**として扱う。

---

## 1.1 従来型プロジェクト管理が得意なこと

一般的なプロジェクト管理は、次のような問いに答えることを得意とする。

- 何をするのか。
- 誰が担当するのか。
- いつまでに行うのか。
- どの状態にあるのか。
- 完了条件は何か。
- どのIssueやPull Requestが関連しているのか。

これらは重要である。作業を分割し、担当を明確にし、進捗を可視化しなければ、プロジェクトは容易に混乱する。特に複数人・複数リポジトリ・複数成果物が関与する場合、Issue tracker や Project board は不可欠である。

しかし、この種の管理が可視化するのは、主に**作業の状態**である。

Issue が open か closed か。Pull Request が merged かどうか。Milestone が達成されたか。Project board のカードがどの列にあるか。これらは運用上の状態を示すが、その変更によってプロジェクトの意味がどう変化したかまでは、必ずしも示さない。

たとえば、あるIssueが完了したとする。しかし、その過程で当初の設計思想が狭められたかもしれない。あるPull Requestがレビューを通過したとする。しかし、実装上の便宜が理論的主張へすり替わったかもしれない。ある文書が読みやすく整理されたとする。しかし、未解決の緊張や判断の痛みが、滑らかな文章の中で消えてしまったかもしれない。

このような変化は、単なる進捗管理の外側にある。

---

## 1.2 AI支援が加速するもの、壊しうるもの

AI支援開発では、この問題がさらに強く現れる。

大規模言語モデルは、Issueの分割、仕様書の起草、Pull Request本文の作成、コード補完、テスト案の生成、ドキュメント整形などを高速化する。これは明らかに有用である。人間だけでは重くなりがちな作業を、短時間で形にできる。

しかし、AIは同時に、プロジェクトの意味を滑らかに変形してしまう。

曖昧な論点を、あたかも解決済みであるかのように書く。仮説にすぎない内容を、確定した設計判断のように整える。意図的に残していた未解決性を、読者に親切な説明へ置き換える。文脈上は重要だった制約を、一般論として読みやすい表現に均してしまう。

このとき問題なのは、AIが間違うことだけではない。むしろ危険なのは、**意味の変化がきれいな文章や整ったコードに隠れて見えなくなること**である。

従来のレビューは、しばしば「正しいか」「動くか」「読みやすいか」「仕様に合っているか」を見る。だがAI支援下では、さらに次を問う必要がある。

- その生成物は、元の意図を保存しているか。
- どこで意味を変換したか。
- その変換は許可されたものか。
- 何を補完したか。
- 何を未解決のまま残したか。
- 何が失われたか。
- その喪失は許容できるか。

Kotonoha Method は、AIを排除する方法ではない。むしろ、AIを使うからこそ必要になる方法である。AIによる生成・要約・整理・実装補助を前提としたうえで、そこで生じる意味変化を人間と制度が引き受けられるようにする。

## 1.3 Gitは必要だが、意味履歴ではない

Gitは強力な履歴管理システムである。どのファイルが、いつ、誰によって、どのように変更されたかを記録できる。branch、commit、merge、revert といった機構は、現代のソフトウェア開発において不可欠である。

しかし、Gitが主に記録するのは、**テキストやファイルの差分**である。

もちろん、commit message や Pull Request 本文を丁寧に書けば、判断の理由や設計意図を残すことはできる。だが、それはGitそのものが意味を理解しているからではない。人間が、その周辺に意味を記述しているからである。

ここに限界がある。

ある文章が削除されたとき、それが単なる冗長表現の整理なのか、重要な思想的射程の喪失なのかは、diffだけからは分からない。ある関数がリファクタリングされたとき、それが設計意図の保存なのか、責任境界の曖昧化なのかは、コード差分だけでは判断できない。ある仕様が短くなったとき、それが明確化なのか、未解決の問いの消去なのかは、行数の増減では分からない。

したがって、Gitは必要である。しかし、それだけでは意味履歴にはならない。

Kotonoha Method は、Gitを置き換えない。Gitの上に、Issue、Pull Request、Decision Record、RDE的レビュー、将来的なSLS-native linkを重ね、テキスト差分を意味差分へ接続する。

短く言えば、次のようになる。

> Git は何が変わったかを記録する。Kotonoha Method は、その変化が意味と責任に何をしたかを問う。

## 1.4 タスク完了と意味完了は違う

プロジェクトにおいて、あるタスクが完了することと、そのタスクが担っていた意味が適切に閉じられることは同じではない。

タスク完了とは、あらかじめ定義された作業が終わることである。コードが実装される。文書が作成される。テストが通る。Issueが閉じられる。

一方、意味完了とは、その作業がもともと担っていた意図、制約、責任、未解決性が、適切に保存・変換・記録されることである。

あるIssueは、実装としては完了していても、意味としては未完了かもしれない。たとえば、設計上の妥協をしたが、その妥協の影響範囲が記録されていない場合である。ある文書は公開可能な品質に見えても、当初の理論的射程を狭めているかもしれない。あるAI生成案は便利でも、その補完が人間の判断として承認されたのか、単なる仮説なのかが曖昧なままかもしれない。

この区別は重要である。

Kotonoha Method では、作業の完了だけでなく、意味の扱いを確認する。すべての変更に重い儀式を課す必要はない。しかし、概念的・制度的・仕様的・責任的に重要な変更では、少なくとも次の観点を確認する。

- 保存された要素は何か。
- 変換された要素は何か。
- 補完された要素は何か。
- 未解決のまま残した要素は何か。
- 失われた要素は何か。
- 逸脱リスクは何か。
- 次回更新では何を引き継ぐべきか。

これは、RDE的レビューの基礎である。

## 1.5 意味統治とは何か

ここでいう「意味統治」とは、意味を中央集権的に固定することではない。

プロジェクトの意味は、常に変化する。最初の構想は、実装上の制約、利用者の反応、レビュー、失敗、技術的発見、AIによる提案によって変わる。変わらないプロジェクトは硬直する。したがって、Kotonoha Method は変化を否定しない。

重要なのは、変化が**見えること**、**説明できること**、**引き受けられること**である。

意味統治とは、プロジェクト内で発生する意味変化を、無秩序な漂流ではなく、追跡可能で評価可能な変化系列として扱うことである。そのためには、変更を単なる作業進捗ではなく、次のような関係の中で見る必要がある。

- 元の意図との関係
- 既存の仕様との関係
- 実装上の制約との関係
- 公開文書の読者との関係
- 責任を負う主体との関係
- 将来の変更との関係

この意味で、Kotonoha Method は、プロジェクト管理を意味統治へ拡張する。

ここでの「統治」は、命令や統制ではない。むしろ、変化を引き受け可能にするための制度的な作法である。

## 1.6 責任が分散しても、帰結は再収束しなければならない

AI協働プロジェクトでは、責任はしばしば分散する。

人間が方針を出す。AIが草案を生成する。別の人間が編集する。レビュアが一部だけを見る。CIがテストを通す。Project boardが進捗を示す。最終的に文書やコードが公開される。

この連鎖の中で、誰が何を決めたのかは曖昧になりやすい。特にAI生成物が介在すると、生成された内容が「提案」なのか「判断」なのか「確定仕様」なのかが混ざりやすい。

Kotonoha Method は、責任の分散そのものを否定しない。現代の開発は、そもそも分散的である。問題は、分散された責任の帰結が、どこにも戻らないことである。

必要なのは、**責任が分散しても、帰結が再収束する構造**である。

たとえば、AIが生成した章案は、そのまま確定文書にはならない。人間がレビューし、RDE的観点で確認し、必要なら未解決性を明示し、公開可能な責任構造へ載せる。Pull Requestがmergeされるときには、その変更がどの意図を保存し、どの意味を変換したかを確認する。仕様変更が行われるときには、その影響を実装・文書・利用者説明へ接続する。

このようにして、責任は分散しながらも、帰結は制度的に再収束する。

---

## 1.7 Kotonoha Method の位置づけ

以上を踏まえると、Kotonoha Method は次のように位置づけられる。

Kotonoha Method は、通常のプロジェクト管理を否定しない。むしろ、それを前提にする。Git、Issue、Pull Request、Project board、Milestone は、運用上の骨格として使う。

そのうえで、Kotonoha Method は、そこに意味の系譜を重ねる。

- Issueを、単なるタスクではなく意味単位として扱う。
- Pull Requestを、単なる差分提出ではなく意味変化の提案として扱う。
- Reviewを、正誤確認だけでなく意味保存・変換・喪失の確認として扱う。
- Documentationを、静的な成果物ではなく更新される意味状態として扱う。
- Project boardを、進捗表示であると同時に意味上のcheckpointを支える補助装置として扱う。
- AI生成物を、作業短縮の道具であると同時に意味変化を生む入力として扱う。

この方法論は、SLSを制度として実装するための実践である。

SLSは意味の系譜を記録する構造である。RDEは意味の変化を評価する構造である。Kotonoha Method は、それらをプロジェクトの日常的な判断、レビュー、記録、責任の中へ接続する。

つまり、Kotonoha Method は、SLSをプロジェクトの制度へ変換する方法である。

---

## 1.8 本章のまとめ

本章では、Kotonoha Method がなぜ必要かを確認した。

従来型プロジェクト管理は、作業状態の可視化に優れている。しかし、AI支援時代のプロジェクトでは、作業の進捗だけではなく、意味の変化を追跡する必要がある。

Gitは不可欠だが、意味履歴そのものではない。Issueは重要だが、閉じられたIssueが意味的にも閉じられたとは限らない。AIは強力だが、意味を滑らかに変形し、未解決性や責任を見えにくくすることがある。

そこで必要になるのが、意味統治である。

Kotonoha Method は、プロジェクトをタスクグラフとしてだけでなく、意味・判断・成果物・責任の系譜として扱う。そして、分散した責任の帰結を、引き受け可能な構造へ再収束させる。

この章の結論は単純である。

> プロジェクトは、完了すればよいのではない。何が変わり、その変化を誰が引き受けるのかを、説明できなければならない。

次章では、この方法論を運用するための中核語彙を整理する。
