# SLS + RDE に基づく開発手法（Kotonoha 自身の事例）

本書は、**Kotonoha** の計画・仕様・実装・公開ドキュメントを進めるときに、**Semantic Lineage System（SLS）** の考え方と **Resonant Deviation Evaluator（RDE）** 型のレビューを、**ソフトウェア実装を待たずに**どう運用しているかを説明する公開資料である。**規範仕様ではない**。API・スキーマの正本は [`kotonoha-spec`](https://github.com/zyx-corporation/kotonoha-spec) に置く。

**English:** [`docs/method/sls_rde_development_method.md`](../method/sls_rde_development_method.md)

---

## 1. 目的

**観念の実践（dogfooding）:** Kotonoha が目指す「意味の系譜」「喪失と逸脱の可視化」を、将来の製品だけでなく **今日の開発プロセス**でも体現する。

- 変更を **文字列差分だけ**として終わらせない。
- **何が保存・変換・補完され、何が未解決のまま残り、何が失われ、どこに逸脱リスクがあるか** を、レビューと記録で落とす。
- その結果を **次の編集・設計・公開判断**へ返す（次回更新方針）。

対象は **仕様文書**、**コード**、**本リポジトリの説明・マニュアル**、および **複数リポジトリ間の整合作業**全体である。

---

## 2. 用語（本書レベルの最小定義）

| 用語 | 本書での意味 |
| --- | --- |
| **SLS** | **意味 lineage** を制度として扱う層。Git／Issue／Project を否定せず、その上に「意味・喪失・逸脱・責任」を載せる発想。 |
| **RDE レビュー** | 変更を **観測カテゴリ**（下記）に沿って読むレビュー。**正誤だけ・ビルドだけ**で終わらせない。 |
| **ΔM（意味変化）** | 文字の増減だけでなく、意図・射程・緊張関係・価値の変化として捉える差分。 |

RDE を **採点器・万能フィルタ・人間の責任の代替**とみなさないこと。

---

## 3. RDE の観測カテゴリ（日常運用への写像）

Issue／PR／文書改訂をレビューするとき、少なくとも次を **後から読めるか** を確認する（順序固定ではない）。

1. **保存された要素** — 意図的に維持した制約・約束。
2. **変換された要素** — 言い換え・構造変更で意味を載せ替えた箇所（暗黙のすり替えでないか）。
3. **補完された要素** — 新しく付与された説明・前提・構造。
4. **未解決のまま残した要素** — 決め切らず残した論点・緊張（「未着手」とは別）。
5. **失われた要素／喪失** — 要約・整理・実装の便宜で薄まった射程・痛み・責任・問い（**削除行だけ**で代替しない）。
6. **逸脱リスク** — 比喩の暴走、RDE の狭義化、戦略と実装の取り違えなど。
7. **次回更新方針** — 次の編集・仕様更新・公開に何を渡すか（一回きりの TODO で終わらせない）。

実務上、**すべてに長文で埋める義務**はない。**重大な喪失や逸脱が「見えない」状態**だけは避ける。

## 4. Git／Issue／Project との役割分担

| 仕組み | 得意なこと | SLS + RDE がメソッドとして足すこと |
| --- | --- | --- |
| **Git** | テキスト差分・コミット | 「何が変わったか」に加え **意味として何が起きたか** を Issue／PR 本文で補う。 |
| **Issue** | 未解決作業・議論 | クローズ時に **未解決・喪失** が議論から消えていないか。 |
| **Projects** | 状態・優先度の可視化 | **完了条件** をボードではなく Issue／PR に残す（各リポジトリの運用に従う）。 |

**Git が「変化」を残すなら、RDE 志向のレビューは「変化が意味と責任に何をしたか」を問う。**

## 5. リポジトリ間の流れ（手法のルーティング）

| リポジトリ | この手法での役割 |
| --- | --- |
| [`kotonoha-spec`](https://github.com/zyx-corporation/kotonoha-spec) | **公開仕様の正本**。外部レビューに耐える規範テキスト。 |
| [`kotonoha-core`](https://github.com/zyx-corporation/kotonoha-core) | 仕様に沿った **実装**。挙動変更は仕様へのトレースを意識する。 |
| **`kotonoha-docs`** | **仕様に含まない**説明・手順・本メソッド。**規範語義をここで静かに書き換えない**。 |
| 非公開の計画・草案 | 公開リポジトリの外で整理し、成熟したものだけを spec／公開ドキュメントへ。 |

## 6. 習慣（軽量）

**作成者**

- 大きめの PR では **意図** と **スコープ外** を書く。
- トレードオフと **意図的に延ばした論点** を diff に埋もれさせない。
- 公開テキストに **内部コードネームや非公開リポジトリへの依存**を必要としないようにする。

**レビュア**

- 概念・編集・アーキテクチャの変更では、**七つの観測**をプロンプトとして使う。
- **RDE** をリンター／小道具に矮小化する変更には抵抗する。

**メンテナ**

- メタファーや運用狭義化など **逸脱リスク** を、レビューの repeating agenda に含める。

---

## 7. 本手法でないもの

- [`kotonoha-spec`](https://github.com/zyx-corporation/kotonoha-spec) の**代替ではない**（振る舞いの規約は spec）。
- **自動ツールが RDE 全体を実装済み**ことを前提にしない（ツール以前にプロセスで適用可能）。
- リポジトリごとの **CONTRIBUTING／テンプレート** に置き換わらない（そこにこの脊髄を載せる）。
