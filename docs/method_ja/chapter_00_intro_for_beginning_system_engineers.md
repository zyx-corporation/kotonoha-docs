# Chapter 0. システム・エンジニアリング初学者のための導入

Status: draft / non-normative

本章は、システム・エンジニアリングを学び始めた読者に向けた導入である。

Kotonoha Method は、いきなり読むと少し抽象的に見えるかもしれない。意味、系譜、RDE、SLS、責任再収束といった語は、通常の入門書にはあまり出てこない。しかし、ここで扱っている問題は、決して特殊な哲学問題ではない。むしろ、日々の開発現場で何度も起きている、きわめて実務的な問題である。

それは、次のような問題である。

- 仕様書には書いてあるのに、実装されたものが微妙に違う。
- Issueは閉じられたのに、なぜその判断をしたのかが後から分からない。
- ドキュメントはきれいになったが、重要な注意点が消えている。
- AIに整理してもらった文章が、元の議論よりも強い主張になっている。
- チームの誰も悪意を持っていないのに、結果として責任の所在が曖昧になる。
- 作業は進んでいるのに、プロジェクトの意図が少しずつ別物になっていく。

システム・エンジニアリングは、こうした問題に向き合うための営みである。

ただし、従来のエンジニアリングは、主に「作るもの」を安定させることに力を注いできた。要求を整理し、設計し、実装し、テストし、運用する。その中で、故障を減らし、品質を高め、再現性を確保し、保守可能にする。これは今でも重要である。

しかし、AI支援開発が一般化し、仕様・コード・文書・判断が高速に生成されるようになると、別の問題が前面に出てくる。

それは、**作られたものが正しく動くか**だけでなく、**その作られたものが、もともと何を意味していたのかを保っているか**という問題である。

Kotonoha Method は、この問題を扱うための方法論である。

---

## 0.1 そもそもシステムとは何か

初学者にとって、最初に理解すべきことは、「システム」とは単なるプログラムではないということである。

システムとは、複数の要素が関係し合い、全体として何らかの振る舞いを生む構造である。ソフトウェア、ハードウェア、ネットワーク、データベース、ユーザー、運用手順、組織、規則、ドキュメント、サポート体制。これらがつながって、はじめて一つのシステムになる。

たとえば、あるWebアプリケーションを考える。

コードだけを見れば、それはプログラムである。しかし実際には、ユーザーが入力し、サーバーが処理し、データベースに保存され、ログが出力され、障害時には運用者が対応し、利用規約が制約を与え、ヘルプページがユーザーの理解を支える。これら全体がシステムである。

つまり、システムとは、機械だけではない。

人間も、文書も、判断も、運用も、責任も、システムの一部である。

この見方は重要である。なぜなら、多くの失敗は、コード単体の失敗ではなく、関係の失敗として起きるからである。

仕様を書いた人はAを想定していた。実装した人はBとして読んだ。テストした人はCだけを確認した。ユーザーはDとして使った。障害が起きたとき、ドキュメントにはEと書いてあった。このように、個々の部品がそれなりに正しくても、関係がずれるとシステムは壊れる。

システム・エンジニアリングは、この関係のずれを減らすための考え方である。

---

## 0.2 エンジニアリングは何を変えるのか

エンジニアリングとは、単にコードを書くことではない。

エンジニアリングとは、不確かな要求や曖昧な期待を、検証可能で運用可能な構造へ変換する営みである。

最初の段階では、多くのものは曖昧である。

「使いやすくしたい」
「安全にしたい」
「AIを活用したい」
「説明可能にしたい」
「ミスを減らしたい」
「現場の負担を下げたい」

これらは出発点としてはよい。しかし、このままでは実装できない。何をもって使いやすいと言うのか。安全とは何に対して安全なのか。AIはどの判断を補助し、どの判断には関与しないのか。説明可能とは誰に対して、どの粒度で、何を説明できることなのか。

エンジニアリングは、この曖昧さを扱う。

ただし、曖昧さを単純に消すわけではない。曖昧なものを無理に確定させると、現実を歪めることがある。重要なのは、曖昧さを区別し、必要な部分を具体化し、残すべき不確実性は不確実性として管理することである。

エンジニアリングが変えるものは、主に三つある。

第一に、願望を構造へ変える。

「便利にしたい」という願望を、画面、API、データ構造、運用手順、テスト条件へ落とし込む。これは、考えを現実に接続する作業である。

第二に、暗黙知を明示知へ変える。

熟練者だけが知っている判断、会議で一度だけ話された前提、チャットの流れの中で決まった制約を、仕様書、Issue、テスト、運用手順として記録する。

第三に、属人的な判断を再現可能な手順へ変える。

誰か一人が分かっているから動く状態ではなく、別の人が見ても理解でき、検証でき、必要なら修正できる状態へ変える。

この三つは、システムを作るうえで不可欠である。

しかし、ここに落とし穴がある。

変換には、必ず喪失が伴う。

願望を構造へ変えるとき、元の曖昧さの一部は消える。暗黙知を明示知へ変えるとき、文脈の豊かさは削られる。属人的な判断を手順へ変えるとき、例外的な感覚や現場の微妙な判断は抜け落ちる。

この喪失は、悪いことだけではない。喪失があるからこそ、システムは実装可能になる。すべての曖昧さを残したままでは、何も作れない。

問題は、何が失われたのかを誰も把握していないことである。

Kotonoha Method は、この変換と喪失を見えるようにする。

## 0.3 これまで何が問題だったのか

従来の開発現場では、多くの問題が「情報共有不足」や「仕様の曖昧さ」として扱われてきた。もちろん、それは間違いではない。しかし、それだけでは十分ではない。

本質的な問題は、情報が不足していることだけではなく、**情報が変化する過程で意味が変わること**である。

たとえば、会議では「ユーザーが自分で判断できるようにする」と話していたとする。その後、Issueには「ユーザーに判断材料を提示する」と書かれる。さらに仕様書では「評価結果を表示する」と表現される。実装では、赤・黄・緑のラベルが表示される。

この流れでは、何かが少しずつ変わっている。

最初の「自分で判断できるようにする」は、ユーザーの主体性を含んでいる。次の「判断材料を提示する」は、まだユーザーの判断を前提にしている。しかし「評価結果を表示する」になると、システム側の評価が中心になる。最後に赤・黄・緑のラベルになると、ユーザーは判断するというより、システムの判定を見る立場になる。

どこか一箇所で大きな間違いが起きたわけではない。むしろ、各段階の変換は自然である。短くし、実装可能にし、分かりやすくしただけである。

しかし、全体としては意味が変わっている。

これが問題である。

これまでの開発では、このような意味変化を十分に扱えてこなかった。なぜなら、開発ツールの多くは、状態と差分を記録するために作られており、意味の変化を記録するためには作られていないからである。

Issue tracker は、作業を管理する。Git は、ファイル差分を管理する。CI は、テスト結果を管理する。Project board は、進捗を管理する。これらは重要である。しかし、「この変更で元の意図がどう変わったか」を直接管理するわけではない。

その結果、次のようなことが起きる。

- 仕様変更の理由が分からなくなる。
- 実装上の妥協が、後から正式な設計思想に見えてしまう。
- ドキュメントの整理によって、重要な警告や未解決性が消える。
- AIが生成した要約が、元の議論よりも断定的になる。
- チームが合意したと思っていた内容が、人によって違う意味で理解される。
- 責任ある判断だったはずのものが、単なる作業履歴に分解される。

これらは、単なる管理ミスではない。

意味の変化を管理対象として扱っていなかったことから生じる、構造的な問題である。

## 0.4 AI支援開発で問題はなぜ大きくなるのか

AI支援開発では、これまで見えにくかった問題が大きくなる。

AIは、曖昧なメモを読みやすい文章にできる。乱雑な議論を章立てにできる。Issueを分解できる。Pull Requestの説明を書ける。コードもテストも生成できる。これは強力である。

しかし、AIは「もっともらしい形」に整えることが得意であるため、未解決のものまで解決済みに見せてしまうことがある。

人間が書いた粗いメモには、ためらいが残っている。言い切れない部分、仮説であること、まだ迷っていることが表面に出る。しかしAIが整理すると、そのためらいは消えやすい。文章は滑らかになり、構造は整い、見出しは立つ。読者は、それを完成度の高い考えだと受け取りやすくなる。

ここで危険なのは、AIが嘘を書くことだけではない。

むしろ、**未確定の判断が、整った文章によって確定済みに見えること**が危険である。

たとえば、AIが「この設計により責任の所在が明確になる」と書くことがある。しかし、実際には「責任の所在を明確にするための手がかりを与える」程度かもしれない。この二つは違う。前者は成果を保証している。後者は支援の範囲を示している。

また、AIが「この方法は安全性を高める」と書くことがある。しかし、何に対する安全性なのか、どの条件で高まるのか、どのリスクは残るのかが明示されていなければ、これは危うい表現である。

AI支援開発では、出力速度が上がる。だが、判断の速度まで本当に上がっているとは限らない。生成は速くなるが、理解、検証、責任の引き受けは、それほど簡単には速くならない。

そのため、AI支援開発では、生成物をそのまま進捗として数えると危険である。

生成された文書は、まだ判断ではない。生成されたコードは、まだ設計の確定ではない。生成されたIssueは、まだ責任ある計画ではない。生成された要約は、まだ元議論の保存を保証しない。

Kotonoha Method は、ここに介入する。

AIを使わないのではない。AIを使うからこそ、生成されたものが元の意図からどう変わったのかを確認する。何が保存され、何が補完され、何が失われたのかを見えるようにする。そうしてはじめて、AI生成物はプロジェクトの中で責任ある成果物へ昇格できる。

## 0.5 エンジニアリングは「作ること」から「変化を管理すること」へ広がる

初学者は、エンジニアリングを「ものを作る技術」として理解しがちである。それは間違いではない。しかし、十分ではない。

エンジニアリングとは、変化を管理する技術でもある。

要求は変わる。利用者は変わる。技術は変わる。組織は変わる。法律や社会的期待も変わる。最初に作った設計は、時間が経てば必ず現実とずれていく。

したがって、よいエンジニアリングは、最初から変化を前提にする。

変更しやすい構造にする。テストで振る舞いを確認できるようにする。ログで状態を追えるようにする。ドキュメントで前提を説明する。Issueで判断の背景を残す。レビューで見落としを減らす。

ここまでは、多くのエンジニアリング実践がすでに扱ってきた。

Kotonoha Method が加えるのは、**意味の変化**である。

要求が変わるとき、意味も変わる。設計が変わるとき、責任境界も変わる。文書が変わるとき、読者の理解も変わる。AI生成物を採用するとき、元の議論の構造も変わる。

だから、これからのエンジニアリングでは、次の問いが必要になる。

- この変更は何を可能にするのか。
- この変更は何を諦めるのか。
- この変更は誰の判断を強め、誰の判断を弱めるのか。
- この変更は元の意図を保存しているのか。
- この変更で失われたものは何か。
- この変更の帰結を誰が引き受けるのか。

これは、従来のエンジニアリングを否定するものではない。

むしろ、エンジニアリングを一段深くする。

コードを動かすだけでなく、判断を追跡する。仕様を固定するだけでなく、仕様がどう変化したかを記録する。AIを使って速く書くだけでなく、速く書かれたものが何を変えてしまったのかを見る。

これが、Kotonoha Method の考えるエンジニアリングである。

---

## 0.6 Kotonohaはエンジニアリングの何を担うのか

Kotonoha は、エンジニアリングそのものを置き換えるものではない。

設計、実装、テスト、運用、セキュリティ、性能改善、ユーザー調査、プロダクト戦略。これらは引き続き必要である。Kotonoha Method は、これらすべてを代行する万能方法論ではない。

Kotonoha が担うのは、これらの作業のあいだで発生する**意味の変化**を扱う部分である。

より具体的には、Kotonoha は次の役割を担う。

第一に、意味の系譜を見えるようにする。

ある判断が、どの議論から生まれ、どのIssueへ入り、どのPull Requestで変化し、どの文書へ反映されたのかを辿れるようにする。これは、単なるリンク集ではない。意味がどう変わったかを追跡するための基盤である。

第二に、変更による意味のずれを観測できるようにする。

元の意図が保存されたのか、別の形へ変換されたのか、新しい仮説が補完されたのか、重要なものが失われたのか。これをレビュー可能にする。ここにRDEの考え方が入る。

第三に、未解決性を消さずに残す。

エンジニアリングでは、すべてを一度に解決することはできない。だからこそ、未解決の問いを「未解決」として残すことが重要になる。Kotonoha は、問いが滑らかな文章や完了ステータスの中で消えることを防ぐ。

第四に、責任を再収束させる。

人間、AI、ツール、文書、レビュー、CIが関与する現代の開発では、責任は分散する。Kotonoha は、その分散を前提にしながら、最終的な判断と帰結がどこへ戻るのかを見えるようにする。

第五に、AI生成物をプロジェクトへ安全に取り込む作法を与える。

AIが作ったものをすぐに確定成果物として扱うのではなく、ドラフト、仮説、補完、変換として読み、必要な確認を経て昇格させる。

この意味で、Kotonoha はエンジニアリングの中でも、**意味・判断・責任の接続層**を担う。

コードを書く層ではない。単なるプロジェクト管理層でもない。仕様、実装、文書、AI生成物、レビュー、運用判断のあいだをつなぎ、そこで生じる意味変化を扱う層である。

## 0.7 初学者が最初に持つべき見取り図

ここまでの議論を、初学者向けに簡単な見取り図として整理する。

まず、従来のエンジニアリングは、主に次を扱ってきた。

| 対象 | 典型的な問い |
| --- | --- |
| 要求 | 何を作るのか |
| 設計 | どう構成するのか |
| 実装 | どう動かすのか |
| テスト | 正しく動くのか |
| 運用 | 安定して使えるのか |
| 保守 | 変更に耐えられるのか |

Kotonoha Method は、そこに次の問いを加える。

| 対象 | Kotonoha Method の問い |
| --- | --- |
| 意図 | 何を守るべきなのか |
| 意味変化 | 何がどう変わったのか |
| 喪失 | 何が見えなくなったのか |
| 未解決性 | 何をまだ決めていないのか |
| AI生成物 | 何を補完し、何を置き換えたのか |
| 責任 | その帰結を誰が、どの構造で引き受けるのか |

この二つは対立しない。

むしろ、後者がなければ、前者はAI支援時代に脆くなる。速く要求を整理し、速く設計し、速く実装し、速く文書化できるようになるほど、何が変わったのかを見失う危険は増える。

初学者は、まず次の区別を持てばよい。

- コードが動くことと、設計意図が保存されていることは違う。
- Issueが閉じることと、問いが解決したことは違う。
- 文書が読みやすいことと、元の議論を正しく保存していることは違う。
- AIがきれいにまとめたことと、人間が責任を持って承認したことは違う。
- 進捗が見えることと、意味の変化が見えることは違う。

この区別を持つだけで、エンジニアリングの見え方は大きく変わる。

## 0.8 小さな例：要望が実装へ変わるまで

最後に、小さな例で考える。

あるチームで、次のような要望が出たとする。

> ユーザーがAIの判断を信頼しすぎないようにしたい。

これは重要な要望である。しかし、このままでは実装できない。そこでIssueが作られる。

> AIの回答に注意ラベルを表示する。

さらに仕様書では、こうなる。

> 回答の信頼度に応じて、低・中・高のラベルを表示する。

実装では、次のようになる。

> confidence score に応じて、緑・黄・赤のバッジを表示する。

一見すると、自然な流れである。しかし、意味は変わっている。

最初の要望は、「ユーザーがAIを信頼しすぎないようにする」だった。これは、ユーザーの判断、AIへの過信、説明、警告、異議申し立て、再確認などを含みうる。Issueでは、それが「注意ラベル」になった。仕様では「信頼度ラベル」になった。実装では「scoreによる色分け」になった。

ここで問うべきことは、実装が悪いかどうかではない。

問うべきことは、何が変わったのかである。

- 「信頼しすぎないようにする」という目的は保存されているか。
- 注意ラベルへの変換は妥当か。
- 低・中・高という分類は誰の判断を表しているのか。
- 色分けは、かえってユーザーに過信を与えないか。
- score の意味は説明されているか。
- ユーザーが異議を出す経路はあるか。
- 失われたものは何か。

このように見ると、エンジニアリングは単に要望を機能へ変える作業ではないことが分かる。

それは、要望の意味を変換しながら、どの変換が許され、どの変換が危険なのかを判断する作業である。

Kotonoha Method は、この判断を支える。

## 0.9 本章のまとめ

本章では、システム・エンジニアリング初学者に向けて、Kotonoha Method の前提を説明した。

システムとは、コードだけではない。人間、文書、運用、判断、責任を含む関係の構造である。エンジニアリングとは、曖昧な願望を、検証可能で運用可能な構造へ変換する営みである。しかし、その変換の過程では、意味が変わり、何かが失われる。

これまでの開発では、作業、差分、進捗、テスト結果は比較的よく管理されてきた。しかし、意味がどう変化したかは、十分に管理されてこなかった。AI支援開発では、この問題がさらに大きくなる。AIは出力を速く整えるが、未確定の判断を確定済みに見せたり、元の議論の緊張を消したりすることがある。

Kotonoha は、エンジニアリングの中で、意味・判断・責任の接続層を担う。

それは、コードを書く代わりではない。Issue管理の代わりでもない。Gitの代わりでもない。むしろ、それらのあいだで生じる意味変化を見えるようにし、評価し、未解決性を残し、責任の帰結を引き受け可能な構造へ再収束させる。

この章の結論は、次の一文にまとめられる。

> エンジニアリングは、作ることだけではない。変化を扱い、その変化の意味と責任を引き受け可能にすることである。

次章では、この考えを踏まえ、従来型のタスク管理から、意味統治としてのKotonoha Method へ進む理由を詳しく見る。
