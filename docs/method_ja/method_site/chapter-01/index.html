タスク管理から意味統治へ

既存のプロジェクト管理を土台にしながら、作業状態ではなく意味状態を扱う方法へ拡張する。

Introduction

本章は、Chapter 0 で示した導入を受けて、Kotonoha Method が既存のプロジェクト管理をどのように拡張するのかを説明する。

Chapter 0 では、システムとはコードだけではなく、人間、文書、運用、判断、責任を含む関係の構造であることを確認した。また、エンジニアリングとは、曖昧な願望を検証可能で運用可能な構造へ変換する営みであり、その変換の過程では意味の変化と喪失が避けられないことを見た。

本章では、その前提を繰り返さない。ここで扱うのは、より実務的な問いである。

既存のタスク管理、Issue管理、Git履歴、Pull Requestレビュー、Project board は有用であるにもかかわらず、なぜそれだけでは不十分なのか。

Kotonoha Method は、既存のプロジェクト管理を否定しない。むしろ、それを前提にする。Git、Issue、Pull Request、Project board、Milestone、Decision Record は、現代の開発において不可欠である。

しかし、それらが主に扱うのは、作業の状態、ファイルの差分、レビューの通過、進捗の可視化である。これらはプロジェクトが「どこまで進んだか」を示すが、プロジェクトが「何に変わったか」を十分には示さない。

Kotonoha Method が扱うのは、この差分である。

  • 作業状態と意味状態の差。
  • タスク完了と意味完了の差。
  • ファイル差分と意味変化の差。
  • 進捗の可視化と責任の可視化の差。
  • AI生成物の流暢さと人間による承認の差。

この章では、タスク管理から意味統治へ進む理由を整理する。

1.1

作業状態と意味状態は違う

一般的なプロジェクト管理は、何をするのか、誰が担当するのか、いつまでに行うのか、どの状態にあるのか、完了条件は何か、優先度はどれほどか、どのIssueやPull Requestが関連しているのか、といった問いに答えることを得意とする。

これらは重要である。作業を分割し、担当を明確にし、進捗を可視化しなければ、プロジェクトは容易に混乱する。特に複数人・複数リポジトリ・複数成果物が関与する場合、Issue tracker や Project board は不可欠である。

たとえば、仕様リポジトリ、実装リポジトリ、公開ドキュメントリポジトリが分かれている場合、ある仕様変更は実装変更を必要とし、実装変更は利用者向け文書の更新を必要とする。このとき、Issueがなければ作業の所在は曖昧になる。Pull Requestがなければ、変更のレビュー単位が不明になる。Milestoneがなければ、どの時点で何を安定させるのかが見えにくくなる。

したがって、Kotonoha Method は既存のプロジェクト管理を軽視しない。むしろ、それを土台として使う。

しかし、この種の管理が可視化するのは、主に作業状態である。Issue が open か closed か。Pull Request が merged かどうか。Milestone が達成されたか。Project board のカードがどの列にあるか。担当者が割り当てられているか。レビューが通ったか。これらは運用上の状態を示す。

だが、その変更によってプロジェクトの意味がどう変化したかまでは、必ずしも示さない。

観点示すもの見落としやすいもの
作業状態どこまで進んだか何に変わったか
意味状態何になったか単純な進捗率

あるIssueが完了したとする。しかし、その過程で当初の設計思想が狭められたかもしれない。あるPull Requestがレビューを通過したとする。しかし、実装上の便宜が理論的主張へすり替わったかもしれない。ある文書が読みやすく整理されたとする。しかし、未解決の緊張や判断の痛みが、滑らかな文章の中で消えてしまったかもしれない。

従来型PMは、このような意味の変化を自動では検出しない。この問いを制度化することが、Kotonoha Method の出発点である。

1.2

「進捗」の影で失われるもの

プロジェクトでは、進捗が見えることは強い誘惑である。Doneの列が増える。Issueが閉じられる。Pull Requestがmergeされる。ドキュメントが整う。デモが動く。これらはチームに安心感を与える。

しかし、進捗の可視化は、ときに別のものを見えにくくする。

未解決性が消える

議論の途中では重要だった問いが、成果物化の過程で「今回は扱わない」「あとで考える」「実装上は不要」とされ、いつの間にか見えなくなる。延期された問いは、記録されなければ、存在しなかったことになる。

判断の痛みが消える

設計上の妥協、思想上の緊張、利用者への影響、倫理的な不確実性は、会話の中では重く扱われていたとしても、最終文書では簡潔な表現に圧縮されがちである。圧縮そのものは悪くない。しかし、圧縮によって痛みが消えると、後から読む人は、その判断がどれほど危うい均衡の上にあったのかを理解できない。

責任の所在がぼやける

IssueではAが提案し、Bが実装し、Cがレビューし、AIが本文を整えたとき、最終的な変更の意味を誰が引き受けるのかが曖昧になる。Git上ではcommit authorやPR authorは残る。しかし、それは責任の全体ではない。

概念の射程が縮む

抽象的な設計思想を実装可能な単位へ落とすことは必要である。しかし、その過程で「実装しやすい形」が「理論の本体」に見えてくることがある。これは特に危険である。実装上の便宜が、いつの間にか方法論の定義へ昇格するからである。

Kotonoha Method は、これらを「進捗の副作用」として扱う。進捗は必要である。しかし進捗は、意味の保存を保証しない。

1.3

Gitは必要だが、意味履歴ではない

Gitは強力な履歴管理システムである。どのファイルが、いつ、誰によって、どのように変更されたかを記録できる。branch、commit、merge、revert といった機構は、現代のソフトウェア開発において不可欠である。

しかし、Gitが主に記録するのは、テキストやファイルの差分である。

もちろん、commit message や Pull Request 本文を丁寧に書けば、判断の理由や設計意図を残すことはできる。だが、それはGitそのものが意味を理解しているからではない。人間が、その周辺に意味を記述しているからである。

ある文章が削除されたとき、それが単なる冗長表現の整理なのか、重要な思想的射程の喪失なのかは、diffだけからは分からない。ある関数がリファクタリングされたとき、それが設計意図の保存なのか、責任境界の曖昧化なのかは、コード差分だけでは判断できない。

たとえば、ある仕様文書から「暫定的に」という語が削除されたとする。diff上では一語の削除にすぎない。しかし意味上は、仮説が確定仕様へ変わった可能性がある。あるいは、単に文章を簡潔にしただけかもしれない。この二つはまったく違う。

したがって、Gitは必要である。しかし、それだけでは意味履歴にはならない。

  1. 重要な変更には意図を記録する。
  2. 変更が意味へ及ぼした影響を記録する。
  3. Issue、Pull Request、Decision Record、文書の間を結びつける。
Git は何が変わったかを記録する。Kotonoha Method は、その変化が意味と責任に何をしたかを問う。

1.4

タスク完了と意味完了は違う

プロジェクトにおいて、あるタスクが完了することと、そのタスクが担っていた意味が適切に閉じられることは同じではない。

タスク完了とは、あらかじめ定義された作業が終わることである。コードが実装される。文書が作成される。テストが通る。Issueが閉じられる。レビューが完了する。Milestoneに含まれる作業がすべてDoneへ移動する。

一方、意味完了とは、その作業がもともと担っていた意図、制約、責任、未解決性が、適切に保存・変換・記録されることである。

あるIssueの目的が「RDEをスコアリング装置として誤解されないように説明する」だったとする。作業の結果として、文書に「RDEは評価を支援する」と書かれた。Issueは完了に見える。しかし、その文書が別の箇所で「RDE score」という表現を導入していれば、意味としては未完了である。作業は終わったが、意図は保存されていない。

Kotonoha Method では、作業の完了だけでなく、意味の扱いを確認する。すべての変更に重い儀式を課す必要はない。しかし、概念的・制度的・仕様的・責任的に重要な変更では、少なくとも次の観点を確認する。

  • 保存された要素は何か。
  • 変換された要素は何か。
  • 補完された要素は何か。
  • 未解決のまま残した要素は何か。
  • 失われた要素は何か。
  • 逸脱リスクは何か。
  • 次回更新では何を引き継ぐべきか。
完了とは、作業が終わることではなく、変化の帰結が次の判断へ引き渡せる状態になることである。

1.5

AI生成物は進捗ではなく、意味変化を含む入力である

Chapter 0 では、AI支援開発において未確定の判断が整った文章により確定済みに見える危険を見た。本章では、それをプロジェクト管理上の問題として扱う。

AI生成物は、進捗に見えやすい。章立てができる。Issueが分解される。Pull Request説明が整う。コードが生成される。テスト案が並ぶ。これらは実際に有用であり、作業速度を大きく上げる。

しかし、AI生成物はそれ自体では、まだプロジェクトの判断ではない。AI生成物は、意味変化を含む入力である。それは提案であり、仮説であり、構造化の補助でありうる。しかし、それがプロジェクトの判断になるためには、レビューと承認が必要である。

したがって、AI生成物をレビューするときは、少なくとも次を問う必要がある。

  • 元の意図を保存しているか。
  • どこで意味を変換したか。
  • その変換は許可されたものか。
  • 何を補完したか。
  • その補完は仮説か、承認済み判断か。
  • 何を未解決のまま残したか。
  • 何が失われたか。
  • 主張が元議論より強くなっていないか。
  • 実装上の便宜が理論的主張へすり替わっていないか。

つまり、AI支援下のプロジェクトでは、生成速度に対応するだけの意味監査能力が必要になる。Kotonoha Method は、そのための制度的実践である。

1.6

RDEは品質評価ではなく、意味変化の観測である

Kotonoha Method において、RDE（Resonant Deviation Evaluator）は中心的な役割を持つ。ただし、RDEを単なる品質評価やスコアリングとして扱ってはならない。

通常のレビューでは、成果物の品質を見る。文書なら読みやすさ、正確性、構成、表記揺れを見る。コードなら動作、テスト、設計、保守性を見る。これらは必要である。しかしRDE的レビューが見るのは、それだけではない。

RDE的レビューが問うのは、変更が意味に何をしたかである。

ある変更は、元の意図を保存したのか。別の形式へ正当に変換したのか。必要な補足を加えたのか。未解決のものを未解決として残したのか。要約や実装の過程で何かを失ったのか。失われたものは許容可能なのか。あるいは、重大な歪曲が起きているのか。

たとえば、元の議論が「SLSは意味履歴を扱うための構想である」だったのに、生成文書が「SLSは意味履歴を完全に保証するシステムである」と書いていれば、これは強すぎる。元の議論が「Kotonoha Methodは責任拡散を見えやすくする」だったのに、生成文書が「Kotonoha Methodは責任問題を解決する」と書いていれば、これも強すぎる。

このような差は、一般的な品質評価では見落とされることがある。文章としては良いからである。しかし意味としては逸脱している。

したがって、RDEは「良い文章か」「良いコードか」だけを見るものではない。それは、元の意図・文脈・責任構造との関係において、変更が何を保存し、何を変え、何を失ったかを見るための観測枠である。

1.7

意味統治とは何か

ここでいう「意味統治」とは、意味を中央集権的に固定することではない。

プロジェクトの意味は、常に変化する。最初の構想は、実装上の制約、利用者の反応、レビュー、失敗、技術的発見、AIによる提案によって変わる。変わらないプロジェクトは硬直する。したがって、Kotonoha Method は変化を否定しない。

問題は、変化することではない。問題は、変化が見えないまま進むことである。あるいは、変化が説明できないことである。さらに危険なのは、変化の帰結を誰も引き受けられないことである。

意味統治とは、プロジェクト内で発生する意味変化を、無秩序な漂流ではなく、追跡可能で評価可能な変化系列として扱うことである。

  • 元の意図との関係
  • 既存の仕様との関係
  • 実装上の制約との関係
  • 公開文書の読者との関係
  • 利用者への影響との関係
  • 責任を負う主体との関係
  • 将来の変更との関係
  • まだ解決していない問いとの関係

ここでの「統治」は、命令や統制ではない。むしろ、変化を引き受け可能にするための制度的な作法である。

1.8

責任が分散しても、帰結は再収束しなければならない

AI協働プロジェクトでは、責任はしばしば分散する。人間が方針を出す。AIが草案を生成する。別の人間が編集する。レビュアが一部だけを見る。CIがテストを通す。Project boardが進捗を示す。最終的に文書やコードが公開される。

この連鎖の中で、誰が何を決めたのかは曖昧になりやすい。特にAI生成物が介在すると、生成された内容が「提案」なのか「判断」なのか「確定仕様」なのかが混ざりやすい。

Kotonoha Method は、責任の分散そのものを否定しない。問題は、分散された責任の帰結が、どこにも戻らないことである。

必要なのは、責任が分散しても、帰結が再収束する構造である。

  1. 承認点を明確にする。
  2. 影響範囲を明確にする。
  3. 未解決性を残す。
  4. 後から検証できるようにする。

このようにして、責任は分散しながらも、帰結は制度的に再収束する。

1.9

具体的な運用イメージ

Kotonoha Method は、抽象概念ではなく日常運用の作法として使う。

Issue作成時

  • このIssueが守るべき意図は何か。
  • このIssueで扱わない範囲は何か。
  • 失ってはいけない前提は何か。
  • 未解決の問いは何か。
  • 完了時に、どの意味状態になっていればよいか。

Pull Request作成時

  • 元の意図から何を保存したか。
  • 何を変換したか。
  • 何を補完したか。
  • 未解決として残したものは何か。
  • 喪失または逸脱リスクはあるか。

レビュー時

  • この変更は、Issueの意図を保存しているか。
  • 主張が強くなりすぎていないか。
  • 未解決の論点が消えていないか。
  • 実装都合が仕様や理論を狭めていないか。
  • AI生成物が人間の承認済み判断に見えていないか。

文書公開時

  • この文書は規範的仕様なのか、非規範的説明なのか。
  • 仮説と確定事項が区別されているか。
  • 内部前提が公開文書へ漏れていないか。
  • 読者に過剰な保証を与えていないか。
  • 将来の更新方針が見えるか。

1.10

本章のまとめ

本章では、Chapter 0 の導入を受けて、従来型のタスク管理から意味統治へ進む理由を整理した。

既存のプロジェクト管理は、作業状態の可視化に優れている。しかし、AI支援時代のプロジェクトでは、作業の進捗だけではなく、意味の変化を追跡する必要がある。

Gitは不可欠だが、意味履歴そのものではない。Issueは重要だが、閉じられたIssueが意味的にも閉じられたとは限らない。Pull Requestは便利だが、mergeされた変更が元の意図を保存しているとは限らない。AIは強力だが、意味を滑らかに変形し、未解決性や責任を見えにくくすることがある。

そこで必要になるのが、意味統治である。Kotonoha Method は、プロジェクトをタスクグラフとしてだけでなく、意味・判断・成果物・責任の系譜として扱う。そして、分散した責任の帰結を、引き受け可能な構造へ再収束させる。

プロジェクトは、完了すればよいのではない。何が変わり、その変化を誰が引き受けるのかを、説明できなければならない。

次章では、この方法論を運用するための中核語彙を整理する。意味、意図、成果物、判断、責任、ΔM、保存、変換、補完、喪失、逸脱といった語を、実務上使える粒度で定義する。
