# Kotonoha Method 表現・公開展開方針

Status: draft / non-normative

この文書は、Kotonoha Method の今後の表現形式、章構成、図表、インタラクティブ要素、紙媒体化を見据えた展開方針を定める。

Kotonoha Method は、まず日本語版の章本文として執筆し、その確認後に英語版を整備する。ただし、最終的な公開形態はMarkdown文書だけに限定しない。将来的には、HTML、JavaScript、SVGを用いた、読者が構造をたどれる表現へ発展させる。

---

## 1. 基本方針

Kotonoha Method は、単なる文章資料ではなく、意味・判断・責任の変化を読者が追跡できる教材兼方法論として整備する。

そのため、今後の展開では次を基本方針とする。

1. **HTML + JavaScript + SVG による記述へ発展させる。**
2. **章は必要に応じてセクション単位へ分割する。**
3. **図表をできるだけ多用する。**
4. **インタラクティブな要素を推奨するが、紙媒体化を見据えた代替表現を必ず考慮する。**

この方針は、Markdown本文を捨てることを意味しない。Markdownは、草稿、レビュー、差分確認、Git管理に適している。一方で、読者体験、教育効果、構造理解、図解表現にはHTML/SVGが有効である。

したがって、初期段階では Markdown を正本に近い編集形式として扱い、将来的に HTML/SVG 版を派生生成する。

---

## 2. HTML + JavaScript + SVG 化の目的

HTML + JavaScript + SVG 化の目的は、見栄えを良くすることだけではない。

Kotonoha Method が扱うのは、作業、意味、判断、責任、未解決性、喪失、逸脱リスクといった相互関係である。これらは、直線的な文章だけでは理解しにくい場合がある。

たとえば、次のような構造は図解に向いている。

- Issue から Pull Request へ意味が圧縮される流れ。
- Git diff と semantic diff の違い。
- Task completion と semantic completion の差。
- AI生成物が draft / hypothesis / accepted decision へ昇格する流れ。
- SLS / RDE / Kotonoha Method / Kotonoha Console の層構造。
- 責任が分散し、レビューと承認を経て再収束する流れ。

SVGは、これらの構造を精密に表現できる。JavaScriptは、図表の切り替え、注釈表示、段階的展開、用語ポップアップ、簡易シミュレーションに使える。

ただし、インタラクティブ表現は本文理解を補助するものであり、本文の代替ではない。

---

## 3. 章からセクションへの分割

現在の章立ては、方法論全体の論理構造を作るための単位である。しかし、HTML/SVG版では、章をそのまま長大な1ページにするとは限らない。

必要に応じて、章を次のようなセクションへ分割する。

- 概念導入
- 典型的な問題
- 実務例
- 図解
- RDE観点
- 運用テンプレート
- 紙媒体向け補足
- 演習またはチェックリスト

たとえば Chapter 1「タスク管理から意味統治へ」は、将来的に次のように分割できる。

| セクション | 内容 |
| --- | --- |
| 1.1 作業状態と意味状態 | Project board / Issue / PR が何を可視化し、何を可視化しないか。 |
| 1.2 進捗の副作用 | 未解決性、判断の痛み、責任、概念射程が失われる構造。 |
| 1.3 Gitと意味履歴 | Git diff と semantic lineage の違い。 |
| 1.4 タスク完了と意味完了 | Done と semantic closure の違い。 |
| 1.5 AI生成物の扱い | 生成物を進捗ではなく意味変化を含む入力として扱う。 |
| 1.6 RDEレビュー | 品質評価ではなく意味変化の観測としてのRDE。 |
| 1.7 運用イメージ | Issue / PR / review / publication の具体例。 |

分割の目的は、章を短くすることではない。読者が意味の階段を踏み外さずに進めるようにすることである。

---

## 4. 図表を多用する方針

Kotonoha Method では、可能な限り図表を用いる。

ただし、図表は装飾ではない。本文の論理を補助し、読者が関係構造を把握するための道具である。

優先して作成する図表は次の通りである。

| 種類 | 用途 |
| --- | --- |
| 層構造図 | SLS / RDE / Kotonoha Method / Kotonoha Console の関係を示す。 |
| フロー図 | 要望、Issue、仕様、実装、文書、レビューの変換過程を示す。 |
| 比較表 | 従来PMとKotonoha Method、Git diffとsemantic diffなどを比較する。 |
| 状態遷移図 | AI生成物が draft / reviewed / accepted / published へ移る過程を示す。 |
| 責任再収束図 | 分散した責任が承認点と記録を通じて再収束する構造を示す。 |
| チェックリスト表 | 実務運用時に確認すべき観点を一覧化する。 |

図表は、可能な限りSVGで作成する。SVGはWeb表示、印刷、拡大縮小に強く、将来のHTML版にも紙媒体版にも転用しやすい。

---

## 5. インタラクティブ要素の扱い

HTML版では、インタラクティブな要素の導入を推奨する。

想定する要素は次の通りである。

- 用語にマウスオーバーしたときの定義表示。
- 図表の段階的表示。
- Git diff と semantic diff の切り替え表示。
- IssueからPR、PRからDecision Recordへの流れをクリックで展開する図。
- RDE観点のチェックリスト表示。
- AI生成物の昇格フローを操作できる簡易ビュー。

ただし、インタラクティブ要素は、理解を補助するためのものである。情報の本体をJavaScriptに閉じ込めてはならない。

JavaScriptが無効でも、基本的な本文と図表が読めることを目標にする。

---

## 6. 紙媒体化を見据えた代替表現

将来的な紙媒体化を見据え、すべてのインタラクティブ要素には代替表現を用意する。

たとえば、Web版でクリックにより段階表示する図は、紙媒体では次のように表現する。

- 段階ごとの静的図を並べる。
- 図の下にステップ表を付ける。
- 重要な分岐を注釈番号で示す。
- クリック展開される説明を脚注またはコラムとして載せる。
- 色だけに依存せず、線種、番号、ラベルでも区別する。

紙媒体化を考慮するため、図表には原則として次を満たすようにする。

- SVGにタイトルと説明を含める。
- 色だけで意味を表現しない。
- 印刷時に白黒でも意味が読める。
- 図表番号を付けられる構造にする。
- 本文中で図表を参照できるようにする。
- インタラクティブ要素には静的版を用意する。

Web版と紙媒体版は同一でなくてよい。しかし、意味内容は一致していなければならない。

---

## 7. Markdown / HTML / SVG の役割分担

当面の役割分担は次のようにする。

| 形式 | 役割 |
| --- | --- |
| Markdown | 草稿、レビュー、Git差分確認、本文正本に近い編集形式。 |
| SVG | 図表、構造図、フロー、比較図。印刷にも転用。 |
| HTML | 公開閲覧、セクション分割、読者導線、図表統合。 |
| JavaScript | 補助的なインタラクション、表示切替、注釈展開。 |
| PDF / 紙媒体 | 将来的な配布、教育資料、冊子化。 |

この分担により、Markdownで意味を安定させ、SVGで構造を可視化し、HTMLで読者体験を整え、紙媒体で長期保存と配布に対応する。

---

## 8. 今後の実装メモ

今後、Kotonoha Method の章本文をHTML/SVG化する際には、次の実装方針を検討する。

- 章ごとに `sections/` を切る。
- 図表を `assets/svg/` に集約する。
- Web用のHTMLは `docs/method_site/` または別ブランチで管理する。
- MarkdownからHTMLを生成する場合は、図表参照とセクションIDを安定させる。
- インタラクティブ要素は progressive enhancement とする。
- 紙媒体版へ変換できるよう、図表番号・キャプション・代替説明を先に設計する。

この段階では、特定の静的サイトジェネレータやビルドツールには依存しない。まずは表現方針と情報構造を安定させる。

---

## 9. 方針の要約

Kotonoha Method は、文章だけでなく図解と操作可能な表現へ発展させる。

ただし、Webインタラクションは本体ではない。意味内容は、Markdown本文、静的SVG、印刷可能な説明としても成立しなければならない。

最終的な目標は、読者が次を追跡できる教材・方法論にすることである。

- 何が変わったのか。
- 何が保存されたのか。
- 何が失われたのか。
- 何が未解決なのか。
- その変化の帰結を誰が引き受けるのか。

HTML、JavaScript、SVGは、その追跡を助けるための表現手段である。Kotonoha Method の中心は、あくまで意味変化と責任構造の可視化にある。
