# はじめての Kotonoha

このページは、Kotonoha を初めて知る人のための入口です。

Kotonoha は、AI や人間が文章・仕様・コードを変更したときに、**何が変わったか**だけでなく、**その変更によって何が保存され、何が失われ、どこに意味のずれが生まれたか**を確認するための仕組みです。

Git は文字列の差分を残します。Kotonoha は、その差分の背後にある意味の変化を扱います。

## まず何を理解すればよいか

最初に覚えることは、次の 3 つだけです。

| 用語 | 最初の理解 |
| --- | --- |
| Kotonoha | 意味の変化を記録・確認するための公開ドキュメントとツール群 |
| RDE | 変更によって意味がずれていないかを見る点検票 |
| SLS | 意味の変更履歴を残す考え方 |

厳密な仕様やデータ構造は、最初から読む必要はありません。まずは「AI が作った要約や実装が、元の意図を変えていないかを確認する仕組み」と考えてください。

## Kotonoha が役に立つ場面

たとえば、次のような場面で使います。

| 場面 | Kotonoha が見ること |
| --- | --- |
| AI に仕様を要約させた | 元の意図や制約が消えていないか |
| AI にコードを生成させた | 実装上の都合が設計思想を変えていないか |
| 議論をドキュメント化した | 未解決の論点を解決済みに見せていないか |
| レビューコメントを反映した | 修正によって別の意味のずれが生まれていないか |

Kotonoha は、AI の出力を自動的に正しいと判定する装置ではありません。人間が判断するための材料を、失われにくい形で残すための仕組みです。

初学者は、最初から次を読む必要はありません。

| 文書 | 後でよい理由 |
| --- | --- |
| Release Train | 配布 baseline やバージョン整合性を確認する段階で読む |
| Acceptance demo | リリース確認や受入検証向けで、学習用ではない |
| CLI installer implementation | メンテナ向けの実装手順 |
| Paper | 背景思想や研究文脈を深く読むための長文 |
| kotonoha-spec | 厳密な仕様・適合性を確認する段階で読む |

## Kotonoha ではないもの

Kotonoha は、次のものではありません。

- Git の代替
- Issue 管理ツールの代替
- AI 出力の自動合否判定器
- 人間の判断や責任の代替
- すべての意味を完全に保存する万能システム

Kotonoha は、既存の Git、Issue、レビュー、ドキュメント作成を置き換えるのではなく、それらの上に「意味の変化を見る層」を追加します。
